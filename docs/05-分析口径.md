# 05 · 分析口径与模拟数据设计

## 1. 为什么先定口径

同一份数据，口径不同会得出不同结论。课程项目最容易出现的三个问题：

1. PV / UV 混用，把“浏览次数”说成“访客数”。
2. 漏斗各步骤独立去重，用户先看详情、后看列表也会被算成“完整漏斗”。
3. 报名成功直接从报名表取，但漏斗第五步从事件取，两个数字对不上。

本模块在接口、报告、AI Prompt 中统一写明口径，并且让模拟数据生成器按同一口径造数。

## 2. 事件模型

一次访问由多条 `visit_event` 组成，核心字段：

| 字段 | 作用 |
| --- | --- |
| `session_id` | 会话；漏斗按它分组，同一 session 内按 `created_at` 排序 |
| `visitor_id` | 设备 / 匿名访客；未登录时用于 UV |
| `user_id` | 登录用户；登录后 UV 按用户去重 |
| `module` | 业务模块：首页 / 车型 / 活动 / 我的 / 智能客服 |
| `action` | `view` / `click` / `favorite` / `signup_click` / `signup_success` / `signup_fail` |
| `page` | 具体页面：`home` / `bike_list` / `bike_detail` / `activity_list` / `activity_detail` / `mine` / `chat` |
| `target_id` | 目标对象，例如活动 ID、车型 ID |
| `duration_ms` | 页面停留；点击 / 报名事件为 0 |
| `channel` | 来源渠道 |

### 2.1 UV 的身份口径

```sql
COALESCE('u:' || user_id, 'v:' || visitor_id)
```

- 登录用户：`u:<user_id>`，同一用户跨设备算一个 UV。
- 匿名访客：`v:<visitor_id>`，按设备 ID 去重。
- 这是课程项目的简化口径；真实生产通常还需要 unionid / 手机号 / 设备指纹做身份图。

## 3. 指标定义

### 3.1 核心指标

| 指标 | 定义 | SQL 口径 |
| --- | --- | --- |
| PV | 页面浏览事件数 | `COUNT(*) WHERE action='view'` |
| UV | 去重访客数 | `COUNT(DISTINCT actor_key) WHERE action='view'` |
| 会话数 | 去重 session 数 | `COUNT(DISTINCT session_id)` |
| 平均停留 | `view` 事件 `duration_ms` 均值 | `AVG(duration_ms) WHERE action='view'` |
| 报名人数 | `signup` 表 `confirmed` 数 | `COUNT(*) WHERE status='confirmed'` |
| 报名/访客转化率 | 报名人数 / UV | `signups / uv * 100` |
| 人均浏览页数 | PV / 会话数 | `pv / sessions` |

> 报名/访客转化率与漏斗总转化率不是同一个指标：前者分母是 UV，后者分母是“进入首页的 session 数”。报告中两者都给出，避免混用。

### 3.2 模块热度

```sql
SELECT module,
       SUM(CASE WHEN action='view' THEN 1 ELSE 0 END) AS pv,
       COUNT(DISTINCT CASE WHEN action='view'
             THEN COALESCE('u:'||user_id, 'v:'||visitor_id) END) AS uv,
       AVG(CASE WHEN action='view' THEN duration_ms END) AS avg_duration
FROM visit_event
WHERE created_at BETWEEN ? AND ?
GROUP BY module
ORDER BY pv DESC;
```

`PV 占比 = 模块 PV / 全站 PV`。热度用于回答“用户主要停留在哪里”，不直接等同于商业价值。

### 3.3 访问趋势

按 UTC+8 自然日聚合：

```sql
strftime('%Y-%m-%d', created_at, '+8 hours') AS day
```

每日返回 PV、UV、会话、报名、报名/访客转化率。默认 14 天，支持 7 / 30 天。

### 3.4 转化漏斗（重点）

**口径：同一 session 内，后一步必须发生在前一步之后；跨 session 不合并。**

五步：

1. 进入首页：`module='home' AND action='view'`
2. 浏览活动列表：`module='activity' AND action='view' AND page='activity_list'`
3. 查看活动详情：`module='activity' AND action='view' AND page='activity_detail'`
4. 点击报名：`action='signup_click'`
5. 报名成功：`action='signup_success'`

SQL 使用 5 段 CTE，每一段都要求 `e.created_at >= 上一步时间`：

```sql
WITH s1 AS (
  SELECT session_id, MIN(created_at) AS t1
  FROM visit_event
  WHERE ... AND module='home' AND action='view'
  GROUP BY session_id
),
s2 AS (
  SELECT s1.session_id, MIN(e.created_at) AS t2
  FROM s1 JOIN visit_event e
    ON e.session_id = s1.session_id AND e.created_at >= s1.t1
  WHERE e.module='activity' AND e.action='view' AND e.page='activity_list'
  GROUP BY s1.session_id
)
-- s3 / s4 / s5 同理
SELECT
  (SELECT COUNT(*) FROM s1) AS step1,
  (SELECT COUNT(*) FROM s2) AS step2,
  ...
```

返回：

- `sessions`：到达该步的会话数。
- `visitors`：到达该步的去重访客数。
- `rateFromStart`：该步 / 第一步。
- `rateFromPrev`：该步 / 上一步。
- `dropRate`：`100 - rateFromPrev`。
- `overallConversion`：第五步 / 第一步。
- `biggestDrop`：流失率最大的相邻步骤。

**为什么按 session 而不是按 user？**

- 按 user 需要跨会话拼接时间线，匿名用户无法稳定识别。
- 按 session 更接近“这一次访问有没有走完”，对页面改版、按钮调优更敏感。
- 代价是跨会话的“先收藏、第二天再来报名”不会被算进同一次漏斗；报告已注明。

### 3.5 渠道

按 `channel` 分会话、事件、报名、报名/会话转化率。渠道值：

`wechat_search`（搜一搜）、`share`（分享）、`qr`（扫码）、`ad`（广告）、`direct`（直接访问）。

## 4. 模拟数据设计

脚本：[`server/src/scripts/generate-mock.js`](../server/src/scripts/generate-mock.js)

### 4.1 可复现

- 使用 `mulberry32` 固定种子伪随机数；同一 `--seed` 生成同一份数据。
- 默认：`--days 30 --sessions 1800 --seed 42`。
- `--clear` 只清 `visit_event`、`is_mock=1` 的报名、旧 AI 解读，**不删真实用户和真实报名**。

```bash
npm run db:reset
npm run mock -- --clear --days 30 --sessions 1800 --seed 42
```

### 4.2 会话路径

每个 session：

1. 100% 进入首页。
2. 56% 概率浏览车型列表；其中 58% 看详情；13% 收藏。
3. 52% 概率浏览活动列表；其中 66% 看详情。
4. 详情页 46% 概率点击报名；点击后按以下条件真实校验：
   - 是否登录；
   - 是否授权手机号；
   - 是否在报名窗口；
   - 是否重复报名；
   - 名额是否已满；
   - 最后 74% 概率真正提交（模拟用户放弃）。
5. 20% 进入「我的」；12% 进入「智能客服」。

所有事件时间按 5—75 秒递增，保证同一 session 内严格有序。

### 4.3 为什么报名只有约 130 条

- 不是每个 session 都会走到活动详情；
- 点击报名后还要经过手机号、时间窗、重复、名额、用户放弃五道筛选；
- 这是刻意设计的“真实漏斗”，而不是让每个 session 都报名成功。

### 4.4 趋势形状

- 周末权重 ×1.28；
- 最近 3 天权重 ×1.22；
- 第 9 天设置一次活动脉冲 ×1.75；
- 其余工作日为基准。

因此趋势图有波动、有峰值，不是一条直线；但所有数字仍由固定种子决定。

### 4.5 数据一致性

- `signup` 只在 `signup_success` 事件前写入；写失败则不写成功事件。
- 报名人数与漏斗第五步可能有 0—2 条差异（例如其他测试直接写报名表、事件缺失）；报告与接口都允许这种边界，并在文档中说明。
- 名额、时间窗、重复报名由真实 SQL 约束校验，不是“假数据随便写”。

### 4.6 数据规模

| 指标 | 默认值 |
| --- | --- |
| 天数 | 30 |
| 会话 | ~1,800 |
| 行为事件 | ~6,000 |
| C 端用户 | 132（12 种子 + 120 模拟） |
| 活动 | 13（10 种子 + 3 历史模拟） |
| 报名 | ~130 |

## 5. 统计结果怎么看

打开 [`reports/analytics_summary.md`](../reports/analytics_summary.md)：

1. **核心指标**：先看 PV/UV/报名/转化率的环比。
2. **模块热度**：首页 / 车型 / 活动三足鼎立，说明流量入口没有过度集中。
3. **趋势**：11-16 有明显峰值（模拟活动脉冲），周末高于工作日。
4. **漏斗**：最大流失在「查看活动详情 → 点击报名」，不是“没人来”，而是“来了不点”。
5. **渠道**：搜一搜与分享贡献主要会话；扫码/广告转化偏低，适合做落地页优化。
6. **AI 解读**：规则兜底版本引用真实数字；配置 Key 后重新生成，结论会更自然，但数字口径不变。

## 6. 口径局限

| 局限 | 影响 | 处理 |
| --- | --- | --- |
| 模拟数据 | 比例与真实业务有偏差 | 报告标注“模拟数据”，confidence=medium |
| session 漏斗 | 跨会话路径不合并 | 文档注明；后续可加 user 级漏斗 |
| 匿名 UV | 清缓存 / 换设备会重复计 | 真实埋点接 unionid / 手机号 |
| 活动维度漏斗 | 第 2 步仍是全站活动列表 | 文档注明；后续加活动曝光事件 |
| 报名成功双源 | 事件表与报名表可能差 1—2 条 | 以报名表为 KPI，以事件表为漏斗；报告同时给出 |
| 时区 | 统一 UTC+8 聚合 | 出海业务需按用户时区 |
